# CLAUDE.md

## 1. Что это за проект

Проект — это система автоматизации обработки документов по поставкам для 3 брендов:

- `moil`
- `moroccanoil`
- `bandi`

Основной пользовательский сценарий:

1. Пользователь загружает документы через Telegram-бота.
2. Бот сохраняет файлы на сервер в структурированные папки.
3. После нажатия `/done` бот отправляет webhook в `n8n`.
4. `n8n` определяет компанию и запускает нужный Python-парсер.
5. Парсер собирает bundle по поставке и возвращает JSON с `invoiceRows`, `packingRows`, `batchRows` и предупреждениями.
6. `n8n` читает мастер-справочник из Google Sheets.
7. `n8n` строит итоговые строки для:
   - таможни
   - Честного Знака
8. `n8n` создаёт недостающие листы в Google Sheets, очищает листы поставки и записывает новые строки.
9. В Telegram отправляется summary об обработке.

## 3. Общая архитектура

### 3.1 Telegram bot
Бот ведёт пользователя по FSM-сценарию:

- выбрать компанию
- выбрать тип документа
- ввести номер поставки
- загрузить документы
- нажать `/done`

Бот:
- сохраняет файлы на сервер
- кладёт их в папку компании и поставки
- формирует `manifest.json` / `shipment_manifest.json`
- по `/done` шлёт POST в webhook n8n
- ограничивает доступ через `ALLOWED_USER_IDS`

### 3.2 Серверное хранение
Файлы хранятся по пути вида:

```text
/opt/tg_uploads/<company>/<shipment_key>/
```

Примеры:

```text
/opt/tg_uploads/moil/42501128/
/opt/tg_uploads/moroccanoil/7260185/
/opt/tg_uploads/bandi/20251201/
```

Внутри папки поставки лежат:
- загруженные файлы
- manifest

### 3.3 n8n
В `n8n` один большой workflow с роутингом по компании:

- MOIL-ветка
- MOROCCANOIL-ветка
- BANDI-ветка

Текущий workflow уже содержит отдельные ветки для всех трёх компаний, отдельные parser-call ноды и отдельные build/write этапы. Для MOROCCANOIL используются ноды `Call Python Parser - MOROCCANOIL`, `Parse Python Output - MOROCCANOIL`, `Read Master Catalog - MOROCCANOIL`, `Build Moroccanoil Customs and CZ Rows`, затем подготовка листов, очистка и запись; для BANDI есть отдельный parser call и отдельная ветка записи DG/NDG/ЧЗ. Для MOIL есть базовая ветка `Call Python Parser -> Parse Python Output -> Read Master Catalog -> Build Customs and CZ Rows -> Prepare Sheet Setup Data -> ...`. fileciteturn37file1 fileciteturn37file0

### 3.4 Python parsers
Сейчас в проекте используются отдельные parser scripts:

- `parse_moil_bundle.py`
- `parse_moroccanoil_bundle.py`
- `parse_bandi_bundle.py`

В текущих версиях MOIL и MOROCCANOIL parsers работают как bundle-parsers по папке поставки, а BANDI parser дополнительно строит split по `DG / NDG / CZ`. fileciteturn37file10 fileciteturn37file5 fileciteturn37file6

## 4.1 MOIL

### Что делает сейчас
- принимает все invoice PDF одной поставки за один запуск
- принимает ровно один общий packing PDF на один запуск
- принимает не более одного общего batch XLSX по поставке
- поддерживает исторический и новый F&O layout документов
- возвращает один bundle на всю поставку
- `n8n` строит:
  - отдельный customs лист для каждого invoice
  - отдельный ЧЗ лист для каждого invoice

### Что уже сделано
- загрузка полного комплекта invoice, общего packing и batch в одну папку
  поставки
- Telegram-бот и n8n требуют хотя бы один invoice, ровно один packing и не
  более одного batch; parser повторяет проверку диагностикой
- если общий packing содержит один SKU в нескольких invoice, build выбирает
  единственный точный набор packing-строк по quantity конкретного invoice
- выбранные packing-строки удаляются из доступного пула перед обработкой
  следующего invoice и не могут быть использованы повторно
- batch связывается с выбранным packing по SSCC, вложенному `IN CB` или
  идентификатору паллеты
- неоднозначный или слишком большой набор не угадывается: используется
  пропорциональный fallback с qty warning
- SKU, разорванные переносом строки в F&O PDF, восстанавливаются
- service-строка `DGR` не считается товаром
- FOC-строки сохраняют нулевую стоимость и полную скидку
- новый Shipping Data Requirements XLSX распознаётся по строке заголовка;
  количество автоматически определяется как коробки или штуки и приводится к
  штукам по соответствующей строке packing
- package/SSCC, barcode, паллета и вложенный carton сохраняются в payload
- строки состава набора сохраняются в порядке invoice с `__isComponent=true`
- компоненты отображаются без `#` и без денежных полей, чтобы не удваивать
  стоимость набора
- batch компонентов набора связывается с component-строкой по описанию
  компонента; родительская строка набора не размножается по component batch

### Ограничения
- `net > gross` в стиле BANDI не реализован
- коробочная логика уровня BANDI не реализована
- внешние carton box (`In <CB>`) отмечаются предупреждением, но не
  распределяются по товарным строкам без однозначных данных поставщика

### Состояние parser
Текущий `parse_moil_bundle.py`:
- ищет invoice/packing/batch по папке поставки
- возвращает единый payload со списками `invoiceRows`, `packingRows`,
  `batchRows` и предупреждениями
- считает валидным один или несколько invoice с ровно одним общим packing
- при валидации не включает компоненты набора в товарный итог invoice

### Состояние n8n build-логики
Исходник MOIL Code-ноды хранится в `workflows/build_moil.js`. Основные
товарные строки сопоставляются с packing/master, а component-строки выводятся
сразу после родительской строки. Денежные поля component-строк должны быть
`null`. Для выбора `totalPriceAfterDiscount` используется nullish-проверка:
значение `0` у FOC нельзя заменять суммой до скидки.

### Инварианты Google Sheets
- `_master_catalog` содержит актуальные SKU поставщика и российские артикулы
- столбец российских артикулов в `_master_catalog` называется `SKU RU`
- шаблоны должны называться строго `TEMPLATE_CUSTOMS` и `TEMPLATE_CZ`
- результирующие листы одной обработки: отдельная пара `<invoiceNo>` и
  `ЧЗ <invoiceNo>` для каждого invoice
- если набор в ЧЗ разделён на несколько pallet/batch-строк, после каждой
  родительской строки повторяется полный состав набора в порядке invoice;
  количество каждого компонента масштабируется на количество блока, а
  денежные и packing-поля компонентов остаются пустыми
- перед массовым изменением `_master_catalog` создаётся скрытая копия;
  неизвестные артикулы, переводы и таможенные данные нельзя придумывать

3. **Просить клиента**: чтобы поставщик хотя бы в пакинге помечал, к какому инвойсу относится

### Что ещё не решено
#### Наборы в BANDI
Клиент прислал справочник наборов `Наборы Банди для Ч З.xlsx` (письмо 25.04.2026).
Структура файла (1 лист, 8 колонок):

```text
GTIN | Артикул | DG/NDG | ТНВЭД | Наименование ENG | Наименование RUS | Volume | тип строки
```

`тип строки` = `набор` или `составляющие`. Сначала идёт строка-набор, под ней — строки-составляющие до пустой строки. На 27.04.2026 в справочнике 4 набора:

```text
BDFV90583 → BDFV90552 (Lotion Baby Cotton 20*20ml)
BDIM26525 → BDIM26402 (Inchmine Lace-up leg mask 5*34g)
BDFV96313 → BDFV96436 (Lotion Peony Blossom 20*20ml)
BDNR97693 → NR77877  (Nordic Deer hand cream 20*20ml)
```

Парсер `parse_bandi_bundle.py` уже умеет находить и читать справочник. По умолчанию ищется в:
1. путь, переданный в `--kits-file`
2. `<input-dir>/Наборы Банди для Ч З.xlsx` (или `bandi_kits.xlsx`, `kits.xlsx`)
3. `/data/bandi/<имя файла>`
4. `/opt/tg_uploads/bandi/<имя файла>`

В payload парсер кладёт:
- `kitsFile` — путь, откуда прочитан справочник (или `null`)
- `kitsCount` — сколько наборов прочитано
- `kitsMapping[]` — массив объектов вида `{ kitVendorCode, kitGtin, ..., components: [...] }`
- В `invoiceRows` / `packingRows` каждой строке проставляется `__isKit: true|false`

Расшифровку (наборы → составляющие) делает build-нода n8n при сборке листа ЧЗ.

### Новые требования по BANDI ЧЗ (письма 24.04 и 25.04.2026)

#### 4.3.1 ЧЗ строится из пакинга, а не из таможни
Сейчас build-нода BANDI делает ЧЗ из таблицы для таможни (агрегация по артикулу).
Нужно строить ЧЗ из строк пакинга — каждая строка пакинга превращается в строку ЧЗ
**после расшифровки наборов и LOT-разбиения**.

#### 4.3.2 LOT-разбиение
Если в пакинге у одного артикула несколько LOT — каждый LOT отдельной строкой
(своё кол-во, своя коробка, свой LOT, своя дата изготовления). НЕ объединять через запятую.

#### 4.3.3 Расшифровка наборов
Если строка пакинга / инвойса соответствует артикулу-набору из `kitsMapping` —
заменить её на N строк-составляющих (N = число составляющих × шт. в наборе).

Например, набор `BDFV90583` (20×20 мл) с qty=10 раскрывается в строку BDFV90552 с qty=200.

Порядок: сначала LOT-разбиение, затем расшифровка наборов (или наоборот — надо проверить
на реальных данных, влияет ли).

#### 4.3.4 Дата изготовления и срок годности
Дата изготовления = парсинг LOT (`YYYYMMDD`) → `DD.MM.YYYY`.
Срок годности = дата изготовления + (36 или 48 месяцев) − 1 день.
Число месяцев берётся из мастер-каталога (колонка «Срок годности»).

#### 4.3.5 Структура листа ЧЗ
Эталон — `Таблица ЧЗ 20260301.xls / packing list` (письмо 25.04). Колонки:

```text
NO. | GTIN | Артикул | DG/NDG | Наименование АНГЛ | Наименование РУС
| LOT | Срок годности (мес) | Дата изготовления | Годен до
| Кол-во | Коробка № | № паллета | Data Matrix | Размер этикетки
| Примечание по этикетке | Концентрация спирта, % ЭТИЛОВЫЙ | Вложения в наборы
```

`Коробка №` для строк, попадающих в коробку с другими артикулами — формат `Часть NN; ` (как в пакинге).

### Новые требования по BANDI таможне (письмо 27.04.2026)

## 5. Telegram bot

### Назначение
Бот нужен для удобной загрузки документов по поставкам.

### Основные возможности
- `/start`
- выбор компании
- выбор типа документа
- ввод номера поставки
- загрузка файлов
- `/done`
- `/cancel`
- вспомогательная команда `/myid`

### Доступ
Ограничение по `ALLOWED_USER_IDS`.

### Переменные окружения
Типовые:

```env
BOT_TOKEN=
UPLOAD_ROOT=/opt/tg_uploads
N8N_WEBHOOK_URL=
ALLOWED_USER_IDS=
```

### Развёртывание
Бот запускается как systemd service.

### Важная история с webhook n8n
Если бот по `/done` получает ошибку вида:
- `The requested webhook "tg-upload-finished" is not registered`

то обычно проблема не в systemd и не в Linux, а в том, что в `.env` прописан test webhook URL вместо production webhook URL.


## 6. n8n workflow

### Общая логика
1. Webhook принимает payload от Telegram bot
2. Workflow normalizes payload
3. Route by company
4. Для каждой компании:
   - call python parser
   - parse python output
   - read master catalog
   - build customs / cz rows
   - prepare sheet names
   - ensure sheets exist
   - clear target sheets
   - append rows
   - send telegram summary

### Важные build-ноды
- `Build Customs and CZ Rows` — MOIL
- `Build Moroccanoil Customs and CZ Rows` — MOROCCANOIL
- `Build Bandi Customs and CZ Rows` — BANDI

### Важные замечания
