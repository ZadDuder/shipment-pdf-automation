## 2026-07-28

### Исправлено

- Исправлена неверная интерпретация результата multi-invoice обработки,
  внедрённая 2026-07-27.
- Полный пакет по-прежнему загружается один раз: все invoice, один общий
  packing и не более одного общего batch-файла.
- Результат снова соответствует рабочему процессу клиента: для каждого
  invoice создаётся отдельная пара `<invoiceNo>` / `ЧЗ <invoiceNo>`.
- Общий packing и batch распределяются между invoice без повторного
  использования одной packing-строки; исправления SSCC/`IN CB`, FOC,
  смешанных единиц batch и компонентов наборов сохранены.
- Расшифровка набора в ЧЗ теперь повторяется непосредственно под каждой
  строкой набора, разделённой по паллете/batch. Компоненты сохраняют порядок
  invoice, получают количество своего блока и не дублируют денежные суммы.
- Создание, очистка и запись всех customs/ЧЗ пар выполняются пакетными
  запросами Google Sheets API.

## 2026-07-27

### Исправлено

- Контракт MOIL приведён к фактическому процессу клиента: один запуск принимает
  полный пакет из одного или нескольких invoice, ровно одного общего packing и
  не более одного batch-файла.
- В этом релизе ЧЗ ошибочно формировался одним общим листом на поставку.
  Контракт отменён исправлением от 2026-07-28.
- Создание, очистка и запись нескольких customs-листов выполняются пакетными
  запросами Google Sheets API, без отдельного полного workflow-прогона на
  каждый invoice.
- Batch сопоставляется с выбранной строкой packing не только по SSCC, но и по
  вложенному `IN CB`. Это исправляет `M101LT100`: 5 FOC-шт. относятся к
  CB `100005636`/паллете 13, а 240 шт. — к SSCC `100004392`/паллете 9.
- Выбранные packing-строки потребляются ровно один раз между invoice; равные
  quantity в нескольких invoice больше не дублируют одну и ту же паллету.
- Несколько packing-строк SKU с общим идентификатором паллеты агрегируются
  перед пересчётом batch из коробок в штуки.
- Shipping Data Requirements автоматически различает quantity в коробках и
  quantity в штуках.
- Batch-строки компонентов наборов связываются с component-строками invoice по
  описанию компонента и больше не размножают родительский SKU набора.
- Добавлены регрессии полного multi-invoice сценария, вложенного CB,
  смешанных единиц batch и набора.

## 2026-07-24

### Исправлено

- Добавлено распознавание нового PDF-формата invoice и packing list F&O в
  MOIL-ветке.
- Восстанавливаются SKU, перенесённые поставщиком на следующую строку.
- Строка логистического сбора `DGR` исключается из товарных позиций с
  диагностическим предупреждением.
- FOC-позиции сохраняют нулевую итоговую стоимость и полную коммерческую
  скидку.
- Строки состава набора сохраняют порядок, остаются без номера и не
  дублируют денежные суммы родительского набора.
- На тот момент был зафиксирован временный контракт `1 invoice + 1 packing`.
  Уточнение клиента от 2026-07-27 заменило его полным multi-invoice пакетом.
- Telegram-бот и Code-нода n8n отклоняют нарушение контракта, а parser
  дополнительно помечает несовпадение количества документов.
- Добавлена поддержка нового Shipping Data Requirements XLSX: динамический
  поиск заголовка, forward-fill SKU/паллета и перевод количества коробок в
  штуки по данным packing list.
- Учтены package/SSCC, GTIN, вложенные carton box и паллеты.
- Явное `boxes=0` для вложенного товара больше не превращается в одну коробку.
- Если общий packing содержит несколько строк одного SKU для разных invoice,
  сборщик сначала выбирает единственный точный набор строк по quantity. Это
  сохраняет исходные boxes, weight и pallet конкретного invoice.
- Exact-subset поиск ограничен по числу строк и состояний. При
  неоднозначности используется пропорциональный fallback с явным
  предупреждением, без молчаливого угадывания.
- Добавлены регрессионные тесты парсера и Code-ноды n8n.

### Безопасность и сопровождение

- Git переведён на allowlist: клиентские документы и credentials не
  индексируются.
- Примеры конфигурации очищены от действующих токенов.
- Webhook больше не передаёт произвольный путь в SSH-команду: компания и номер
  поставки валидируются, серверный путь строится внутри workflow.
- Добавлена документация по локальной проверке и production-релизу.
